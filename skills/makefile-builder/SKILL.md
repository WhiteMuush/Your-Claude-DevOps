# Orchestration Makefile

## Principle

An orchestration Makefile **declares and wires, it does not execute**. Every decision goes down into a script, which can be read without knowing Make and debugged by running it on its own.

As soon as it grows beyond a few targets, it is split into included fragments, one per component.

## Structure

```
Makefile                 configuration, includes, nothing else
makefiles/
  common.mk              what belongs to no component
  component.mk           what the components share
  infra.mk               one fragment per component
  backend.mk
  frontend.mk
scripts/
  lib.sh                 sourced by the others: output, log, guardrails
  <action>.sh            one action, one script
```

Root:

```make
SHELL := /usr/bin/env bash
.SHELLFLAGS := -euo pipefail -c
.DEFAULT_GOAL := help

ORG      ?= my-org
LOG_FILE ?= .logs/pipeline.log
PIPELINE := scripts

# Exported, never passed positionally: the scripts read the environment.
export ORG LOG_FILE

include makefiles/component.mk
include makefiles/backend.mk
include makefiles/common.mk
```

`help` as the default target: a bare `make` lists, it does not deploy.

## Configuration: export, do not pass positionally

The most expensive mistake observed. Scripts end up with `(( $# == 7 ))` and `repos=("$1" "$3" "$5")`, and adding a component breaks the arity of every caller.

```make
# NO: fragile arity, unreadable, does not scale
check:
	@scripts/check.sh "$(R1)" "$(W1)" "$(R2)" "$(W2)" "$(R3)" "$(W3)" "$(REF)"

# YES: exported once at the root, read by the script
check:
	@scripts/check.sh
```

Arguments are kept for what varies **per call**, not for configuration.

## Factor without breaking the help

Six nearly identical `deploy-*` and `teardown-*` targets is the classic flaw. But **a target generated by `$(eval)` is invisible in the help**, because the help reads the source text of the files.

So the factoring goes into the call, not into the declaration:

```make
# component.mk
run = $(PIPELINE)/dispatch.sh --repo "$(ORG)/$(1)" --workflow "$(2)" --label "$(3)"

# backend.mk
backend: ## Build and deploy the backend
	@$(call run,$(BACKEND_REPO),ci-cd.yml,backend)
```

Three readable lines per component, a single definition of the command.

## Self-documenting help

Never a list of `@echo`: it drifts from the real targets. `##@` sections, `##` descriptions, a script that parses the Makefile and its includes.

```make
##@ Deploy

deploy: ## Deploy everything in order
	@$(MAKE) infra
```

The script **collects then groups** before printing: a section is declared in the fragment that owns the target, so it appears in several files, and printing as you go repeats its headers. Drive color **and** order from a single `Section=color` list.

## Order: recursive make, not prerequisites

```make
# NO: make can reorder or parallelize. .NOTPARALLEL is a global hammer.
deploy: infra backend frontend

# YES: the order is the point, so it is written down
deploy:
	@$(MAKE) infra
	@$(MAKE) backend
	@$(MAKE) frontend
```

## Output contract: Ansible's

Reuse its vocabulary, its palette and its `PLAY RECAP`. It already answers the questions an operator asks.

| Outcome | Meaning | Color |
|---|---|---|
| `ok` | already in the desired state, nothing done | green |
| `changed` | was not, this run changed it | yellow |
| `skipping` | does not apply, or cannot be evaluated here | cyan |
| `unreachable` | the thing could not be contacted | bright red |
| `fatal` | contacted, evaluated, and it is wrong | red |

The two that everyone forgets are the two that matter:

- **`changed` makes idempotence visible.** A second run at `changed=0` proves it, where a comment only claims it.
- **`unreachable` separates the network from the configuration.** Without it, a silent API is reported as a broken config, and that false alarm is what makes people stop reading the output.

```
TASK [github : workflows can be triggered by hand] *****************
fatal:       [backend] ci-cd.yml has no workflow_dispatch
             add it, and widen the 'if: github.event_name' guards

PLAY RECAP ********************************************************
doctor      : ok=11  unreachable=0   failed=4   skipped=0
```

### The words come from the tool, the form comes from Ansible

Ansible provides the **form**: `TASK [...]`, one outcome per line, the palette, the `PLAY RECAP`, the exit code. The **words** for outcomes and counters are chosen according to what is running, so that every number answers a question the operator asks about that tool.

The recipe:

1. List what the operator wants to know after a run of this specific tool.
2. One counter per answer, named with the tool's vocabulary.
3. Map each counter to a palette color: green = desired state, yellow = something changes or will change, cyan = not applicable, bright red = unreachable, red = wrong or failed.
4. Keep a single counter that proves idempotence: the changes counter, which must be 0 on the second run, whatever its name.
5. A counter that can never go above 0 for this tool does not appear.

| What is running | Adapted recap |
|---|---|
| Read-only diagnostic | `doctor : ok=11  unreachable=0  failed=4  skipped=0` |
| Terraform plan / apply | `terraform : checked=3  add=1  change=0  destroy=0  applied=1  failed=0` |
| Helm deployment | `helm : installed=1  upgraded=2  unchanged=3  failed=0` |
| Test suite | `tests : passed=42  failed=1  skipped=3` |

Per-line outcomes follow the same logic: `to add:`, `applied:`, `upgraded:`, `passed:` when these words describe what happened better than `ok:` or `changed:`.

The exit code is the machine interface: non-zero if `failed` or `unreachable`. **`skipped` never causes a failure**: not applicable is not wrong.

Provide a `doctor` target that does not stop at the first problem: learning everything in one pass is its whole point. All the other targets stop at the first one.

## Mandatory log file

```make
LOG_FILE ?= .logs/pipeline.log
export LOG_FILE
```

- **Append**, never truncate: the previous attempt explains this one
- Timestamped header per run, **and a timestamp per line**
- **No ANSI sequences**: the terminal keeps its colors, the file stays greppable
- `chmod 600`, and never a token in it
- **Write directly, not through `tee` and process substitution**: that setup loses its end when the shell exits before the writer has drained, and the end of the log is exactly what you come looking for
- Add `.logs/` to `.gitignore`

## Common mistakes

| Mistake | Consequence |
|---|---|
| Everything in a single Makefile | Unreadable from the tenth target on, no separation by component |
| Configuration as positional arguments | Fragile arity, one more component breaks every caller |
| Targets generated by `$(eval)` | Invisible in a help that reads the source |
| `help` written with `@echo` | Silently drifts from the real targets |
| Order expressed as prerequisites | Make is free to reorder, `.NOTPARALLEL` hides the problem |
| `A && B \|\| C` as if-then-else | C also runs if B fails, the counters become wrong |
| No changes counter | Idempotence stays an invisible intention |
| No log file | The incident output disappeared with the terminal |
| Depending on `jq` | `gh --jq` and `az --query` already do it |

## Verify

```bash
make            # lists, does not deploy
make lint       # shellcheck -x, with # shellcheck source= above each source
<script>        # runs on its own, outside of make
<script>        # twice: on the second run, the changes counter is 0
```

**REQUIRED BACKGROUND:** for the content of the scripts themselves, stdout/stderr contract, guardrails, idempotence, use `bash-script-builder`.
